# ペルソナ: 執筆環境 / CMS 戦略

## P1: 著者

### 概要

個人技術ブログの主な執筆者。PC での本格執筆を中心に、スマートフォンでは軽微な修正や公開確認を行う。

### 目的

- microCMS の UI に縛られず、Obsidian / VS Code など慣れた外部エディタで記事を書きたい。
- Markdown / MDX の記事を Git 管理し、変更履歴を追える状態にしたい。
- 公開前に本番に近い見た目でプレビューしたい。
- PR と Vercel の自動デプロイを使い、手作業の公開作業を減らしたい。

### 課題

- microCMS の編集 UI が書きづらい。
- Git ベースは魅力的だが、毎回のデプロイ操作が面倒になる懸念がある。
- 下書きが公開面に混入する事故は避けたい。
- 画像管理は今すぐ決めきれないため、本文執筆の改善を先に進めたい。

### 関連ストーリー

- US-1: Markdown / MDX 記事ファイルを作成できる
- US-2: 記事 frontmatter を検証できる
- US-3: 外部エディタで書いた記事をプレビューできる
- US-4: Pull Request で記事を公開できる
- US-5: 下書き記事を公開面から除外できる
- US-8: 将来の画像管理方式を妨げずにアイキャッチを扱える

## P2: サイト運用者 / 開発者

### 概要

Astro + TypeScript + Vercel + microCMS + Firebase で構成された既存ブログを保守する人。執筆体験を改善しつつ、既存機能と運用安定性を維持する責任を持つ。

### 目的

- ブログ記事だけを Git 管理へ移行し、プロフィールとプロジェクトは microCMS に残したい。
- 既存のブログ一覧、詳細、カテゴリ、検索、RSS、サイトマップを壊さずに記事取得層を切り替えたい。
- frontmatter の型とバリデーションを整備し、不正な記事データをビルド時に検出したい。
- GitHub / Vercel / 将来の管理 UI に関する認証・認可・トークン管理を安全に設計したい。

### 課題

- 既存の `src/lib/microcms.ts` と新しい Markdown / MDX 記事取得層の責務が混ざると保守しづらい。
- Firebase のリアクション、閲覧数、ブックマークは記事 ID に依存するため、移行時の互換性が必要。
- 既存 microCMS 記事の移行では slug、公開日、カテゴリ、アイキャッチ参照を維持する必要がある。
- セキュリティ要件を実装後に後付けすると手戻りが大きい。

### 関連ストーリー

- US-2: 記事 frontmatter を検証できる
- US-5: 下書き記事を公開面から除外できる
- US-6: 既存 microCMS 記事を Markdown / MDX へ移行できる
- US-7: microCMS と Git 管理記事を責務分離して共存できる
- US-9: 記事 ID と既存動的データの互換性を維持できる
- US-10: 認証・シークレット管理のセキュリティ条件を満たせる

## P3: 読者

### 概要

ブログ記事を読む利用者。執筆環境の変更そのものは意識しないが、公開記事の品質、URL の安定性、検索や RSS の正確性に影響を受ける。

### 目的

- 既存記事の URL やカテゴリ導線が壊れず、これまで通り記事を読める。
- 下書きや未完成記事ではなく、公開済みの記事だけを閲覧できる。
- RSS、検索、サイトマップに公開済み記事だけが載る。
- ページ表示速度や本文表示が悪化しない。

### 課題

- コンテンツ移行によって既存リンクが壊れると記事に到達できない。
- 下書き記事が誤って公開されると信頼性が下がる。
- Markdown / MDX 化によって本文表示やコードブロックの見た目が崩れる可能性がある。

### 関連ストーリー

- US-3: 外部エディタで書いた記事をプレビューできる
- US-5: 下書き記事を公開面から除外できる
- US-6: 既存 microCMS 記事を Markdown / MDX へ移行できる
- US-9: 記事 ID と既存動的データの互換性を維持できる
